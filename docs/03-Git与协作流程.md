# 03 Git 与协作流程

> 这一份解决两个问题：**代码怎么管**，以及**一个人在没人配合的情况下，怎么把公司那套流程真实地走一遍**。
> 不是让你背名词，是让你在面试里说出"我们当时是这么干的"，并且拿得出证据（PR、提测单、上线单、复盘）。

---

## 1. 国内普通公司的真实流程长什么样

小团队（5~15 人）一个迭代的常态，不是大厂那套重量级流程：

```
周一  需求评审（30~60min）→ 你大概知道要做什么了
周一  技术方案/表设计过一下（口头 + 文档）→ 定接口、定表
周一  排期（口头："这个周五能给吗"）→ 写进 Jira/禅道/Teambition
周二~周四  开发：拉分支 → 写码 → 自测 → 提 PR → 同事 CR → 改 → 合 main
周四下午  提测：给测试一个版本 + 提测单（改了什么、影响哪些功能、已知问题）
周四~周五  测试提 bug → 修 → 回归 → 打 tag 发版
周五  上线（小公司常常是后端自己部署）→ 盯日志 → 有问题回滚
下周一  复盘 15min：哪个 bug 是可以避免的
```

**和你在对日项目里的差别**（这几点就是你换赛道要适应的）：

| 对日外包 | 国内中小公司 |
|---|---|
| 式样书极细，照做即可 | 需求经常一句话，**要你自己补细节并确认** |
| 单体测试由开发写完交测试 | 自测 + 单测都算你的，出问题先找你 |
| 变更走严格的申请流程 | 变更快，但**你要自己判断影响面** |
| 注重"不出错" | 注重"快速交付 + 出问题能兜住" |
| 文档是交付物 | 文档是沟通工具，够用就行 |

**你的优势别丢**：写清楚文档、测试覆盖全、改动前先想影响面——这三样在快速迭代的团队里非常稀缺，是新人最快被信任的方式。

**你要补的**：主动决策（别等着别人给式样书）、自己排期、自己判断"够不够上线"。

## 2. 一个人怎么模拟一整个团队

| 公司里的角色 | 你找谁演 | 怎么演才不像过家家 |
|---|---|---|
| 产品经理 | AI（prompt 见第 4 节） | 只给你一句话需求，且**不告诉你边界情况**，逼你问 |
| 测试 | AI + 你自己 | 让 AI 按"我要弄坏它"的思路出用例，而不是"验证它能用" |
| 技术负责人 / Reviewer | AI | 让它只挑刺不给答案，你改完再给它看 |
| 项目经理 | 你自己 + 日历 | 排期写成具体日期，延期了就在日报里写原因 |
| 运维 | 你自己 | 上线单、回滚方案必须写，不能"应该没问题" |

**关键**：每个阶段要产出一个**文件**。没有文件的流程等于没发生，面试时也拿不出证据。

```
fixdesk/
├── docs/
│   ├── review/        需求评审记录（D1）
│   ├── design/        接口契约、性能记录（D2、D14）
│   ├── test/          测试用例、提测单（D12）
│   ├── postmortem/    故障复盘（D17、D18）
│   ├── release/       上线单、回滚记录（D20）
│   └── retro/         周复盘、项目复盘（D21）
├── sql/schema.sql
├── src/
└── blockers.md        卡住的事，每天更新
```

## 3. 每个阶段的产出物（模板，直接抄）

### 3.1 需求评审记录 `docs/review/D1-需求评审.md`

```markdown
# 需求评审记录 2026-10-24
参会：产品(AI)、测试(AI)、开发(我)
需求版本：v1

## 评审意见
| # | 提出人 | 意见 | 结论 | 理由 |
|---|---|---|---|---|
| 1 | 测试 | 工单撤销后能否重新打开？没说 | 不采纳 | 撤销即终态，需要重新提单，避免状态回退带来的数据不一致 |
| 2 | 产品 | 技术员离职了，他名下的单怎么办 | 采纳 | 管理员可改派（ASSIGNED 态允许改派），写进 U08 |
| 3 | 测试 | 同一人 5 秒内重复点提交会生成两张单 | 采纳(降级) | 本期靠前端置灰，后端不加幂等，记入已知问题 |

## 被驳回的需求
- 附件上传：本期不做，对象存储成本与收益不匹配

## 影响排期的点
- 改派逻辑让 D7 多 0.5h
```

### 3.2 排期表（写在 Issue 里，或 `docs/plan.md`）

| 任务 | 预估 | 计划完成 | 依赖 | 风险 |
|---|---|---|---|---|
| 登录 + JWT | 1.5h | 10-27 | 骨架 | 密钥长度踩坑 |

## 4. AI 角色扮演的三个 prompt（照抄，按需改）

**① 产品经理（只给模糊需求，逼你问）**

```
你是一家 50 人公司的产品经理。公司现在用微信群报修，要做一个内部工单系统。
请你只给我一段 100 字以内的口语化需求描述，不要给字段、不要给边界条件、不要给流程。
我提问时你再回答，回答要像真实产品经理：有的能立刻答，有的说"这个你定"，有的会改需求。
```

**② 测试（目标是弄坏它）**

```
你是测试工程师，负责一个报修工单系统。接口契约如下：<粘贴接口清单>
请按"我要弄坏它"的思路，设计 20 条测试用例，覆盖：状态跳变、越权、并发、边界值、特殊字符、空值。
用表格输出：编号/场景/步骤/期望结果/优先级。不要写"验证功能正常"这种废话用例。
```

**③ 技术负责人（只挑刺，不给答案）**

```
你是技术负责人，review 一个工作 3 个月的后端新人的 PR。他的代码：<粘贴 diff 或文件>
请按真实 code review 的风格，挑 5 个问题，按严重程度排序。每个问题说清"哪里有问题、会导致什么后果"，但不要直接给我正确代码。
重点看：事务边界、异常处理、权限校验、SQL 索引、命名。
```

## 5. Git：装、配、用

### 5.1 装与配（你机器上还没装）

```powershell
winget install --id Git.Git -e
# 装完重开终端
git --version

git config --global user.name  "你的名字"
git config --global user.email "你的邮箱"        # 要和 Gitee/GitHub 一致
git config --global core.autocrlf true           # Windows 换行，避免整个文件显示改动
git config --global init.defaultBranch main
git config --global pull.rebase true             # 拉取用 rebase，历史干净
```

**SSH（推代码不用每次输密码）**

```powershell
ssh-keygen -t ed25519 -C "你的邮箱"      # 一路回车
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub   # 复制输出
# 粘贴到 Gitee「设置 → SSH 公钥」或 GitHub「Settings → SSH keys」
ssh -T git@gitee.com                      # 看到 successfully 就行
```

**Maven 阿里云镜像**（不配的话第一次下依赖能等半小时）

`C:\Users\<你>\.m2\settings.xml`：

```xml
<settings>
  <mirrors>
    <mirror>
      <id>aliyun</id>
      <mirrorOf>central</mirrorOf>
      <name>aliyun central</name>
      <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
  </mirrors>
</settings>
```

### 5.2 分支模型：main + feature，不要 develop

```
main         ← 永远可运行、可发布；保护分支，只能通过 PR 合入
 ├─ feature/07-state-machine
 ├─ fix/17-concurrent-accept
 └─ chore/19-deploy
tag: v0.1.0  v0.5.0  v0.9.0  v1.0.0
```

为什么不要 `develop`：一个人开发，多一个长期分支就多一次合并；`main` 随时可发布反而逼你每个 PR 都保证能跑。团队 ≥3 人、需要并行发版时再引入。

**命名**：`feature/<Issue号>-<短描述>`、`fix/<Issue号>-<短描述>`、`chore/...`、`docs/...`、`test/...`。全小写，用连字符。

### 5.3 commit 规范（Conventional Commits，中文描述）

```
<type>(<scope>): <subject>

<body 可选：为什么改，不是改了什么>

<footer 可选：Closes #12>
```

| type | 用在哪 |
|---|---|
| feat | 新功能 |
| fix | 修 bug |
| docs | 文档 |
| test | 测试 |
| refactor | 不改行为的重构 |
| chore | 构建、依赖、配置、脚本 |
| perf | 性能优化 |

好的：

```
feat(ticket): 新增派单与接单接口

- 引入 TicketStatus 枚举约束合法流转
- 用 where status = ? 做 CAS 更新，影响行数为 0 抛 40901
- 每次流转写 ticket_log

Closes #8
```

坏的（面试官一看就知道你没在团队里写过代码）：

```
update
修改
fix bug
提交代码
feat: 完成了很多功能
```

**粒度**：一个 commit 做一件事。判断标准——**能不能用一句话说清，且回滚它不会带走别的东西**。一天 1~3 个 commit 是正常的。

**提交时机**：编译通过 + 自测过。别提交"半截代码"，尤其别在 main 上。

### 5.4 PR（一个人也要开）

流程：

```bash
git switch main && git pull
git switch -c feature/07-state-machine
# ... 写代码 ...
git add -A && git commit -m "feat(ticket): 状态机与 CAS 流转"
git push -u origin feature/07-state-machine
# 到 Gitee/GitHub 网页开 PR
```

PR 描述模板：

```markdown
## 关联
Closes #7

## 改了什么
- 新增 TicketStatus 枚举 + canTransferTo
- 抽 transition() 统一做 CAS 更新
- assign / accept 两个接口

## 怎么自测的
- [x] 正常路径：CREATED → ASSIGNED → PROCESSING
- [x] 非法跳变：CREATED → COMPLETED，返回 40901
- [x] 重复接单：第二次 40901
- [x] 并发 20 次 accept，只有 1 次成功

## 影响面
- 工单状态字段取值新增两个，老数据不受影响
- 无 DB 结构变更

## 自查
- [ ] 无先查再改的并发漏洞
- [ ] 事务内没有远程调用/文件 IO
- [ ] 参数都校验了
- [ ] 没有硬编码密码/密钥
```

**Code Review 自查清单**（每次 PR 前过一遍，这 10 条能挡掉 80% 的低级问题）：

1. 有没有"先查后改"的并发窗口？
2. 事务边界对不对？异常有没有被吞？
3. 按 ID 的操作有没有校验归属（不只是列表过滤）？
4. 有没有 `SELECT *`、`LIKE '%x%'`、`${}` 拼接？
5. 新加的查询条件有对应索引吗？
6. 异常是否都走了统一处理？有没有把堆栈返给前端？
7. 日志够不够定位问题？有没有打印敏感信息？
8. 命名是否表达意图（`list` → `pageTickets`）？
9. 魔法值是否提成枚举/常量？
10. 有没有留下 `System.out`、注释掉的代码、`TODO` 没写原因？

### 5.5 Issue 与看板

标签：`feat` `bug` `tech` `docs` + 优先级 `P0/P1/P2`。
一张 Issue = 一个可验收的活（对应 01 文档的 15 个用例）。开发时 commit 里写 `#12`，PR 合并自动关单。

### 5.6 版本号与 tag

`v0.1.0`（骨架+登录+提单）→ `v0.5.0`（全流程+权限）→ `v0.9.0`（导出/统计/定时）→ `v1.0.0`（上线）。
语义化版本：`主.次.修`，`0.x` 表示还在开发中。

```bash
git tag -a v0.5.0 -m "全流程闭环 + 数据权限"
git push origin v0.5.0
```

### 5.7 常用命令速查（够你用 4 周）

```bash
# 看状态 / 看差异
git status
git diff                    # 未暂存的改动
git diff --staged           # 已暂存的改动

# 提交（推荐 -v 看一遍 diff 再写 message）
git add -p                  # 分块暂存，避免把调试代码一起提交
git commit -v

# 改错了
git commit --amend          # 改最后一次提交（还没 push 时）
git restore <file>          # 丢弃工作区改动
git restore --staged <file> # 取消暂存
git reset --soft HEAD~1     # 撤销提交但保留改动

# 分支
git switch -c feature/x     # 建并切
git branch -d feature/x     # 删本地分支（已合并）
git push origin --delete feature/x

# 同步
git fetch --prune
git rebase origin/main      # 自己的分支跟上 main

# 回滚（生产用这个）
git revert <commit>         # 生成一个反向提交，不改历史
git log --oneline --graph --all

# 找问题
git log -S "关键字"          # 哪次提交引入/删除了这段代码
git blame <file>            # 每行是谁改的
git show <commit> --stat
```

**规矩**：`main` 上永远不要 `push -f`；已经 push 的公共分支不要 rebase。

### 5.8 `.gitignore`（已放在仓库根目录）

关键几条：`target/`、`.idea/`、`*.iml`、`application-local.yml`、`*.log`、`.env`。
**提交前自查**：`git status` 里出现 `.class`、`target`、`.idea` 说明 ignore 没生效。

### 5.9 绝对不能进 Git 的东西

| 东西 | 后果 | 正确做法 |
|---|---|---|
| 数据库密码 | 泄露；面试官看到会扣分 | 环境变量 / `application-local.yml`（已在 ignore） |
| JWT 密钥 | 同上 | 环境变量，本地放 local 配置 |
| `target/`、jar | 仓库暴涨 | ignore |
| 公司代码 | 违法，真的会出事 | 这条最重要：**只用自己写的东西练习** |

已经提交了怎么办：改配置 + `git rm --cached`，如果推到公开仓库了，**立即改密码**，历史清理（BFG/filter-repo）只是补救。

## 7. 如果公司用的是 GitLab / 禅道 / Jenkins

| 本方案 | 公司里对应 | 差别 |
|---|---|---|
| Gitee PR | GitLab Merge Request | 概念一样，MR + Approve |
| Gitee Issue | Jira / 禅道 / Teambition | 一样，字段更多 |
| 本地 `mvn package` + 手动部署 | Jenkins / GitLab CI / 阿里云效 | 有流水线后，合 main 自动构建部署 |
| `docs/release/上线单.md` | 发布系统里的发布单 | 一样，必须有回滚方案 |
| 日报 | 钉钉/飞书日报、周会 | 一样 |

面试被问"你们怎么发版"，答"本地打包 → 传服务器 → 重启 → 冒烟"，这是小公司真实答案，比背 Jenkins 流水线名词可信。

## 8. 十二个坑（大概率你会踩一半）

1. `git add .` 把 `.idea`、`target` 全提交了 → 先写 `.gitignore` 再写代码。
2. 第一天就把 `.gitignore` 忘了，后面清理历史很麻烦。
3. commit message 写"update" → 三个月后自己都看不懂。
4. 在 main 上直接改，改崩了没处回。
5. 一个 PR 塞 8 个功能，自己 review 都看不下去 → 按 Issue 拆。
6. 本地跑通就合 main，没跑冒烟。
7. 配置文件里的密码提交上去 → 当成事故。
8. 合并时冲突乱删代码 → 冲突先看两边意图，别直接 `--ours`。
9. `git push -f` 到 main，把别人（未来是你自己）的提交冲掉。
10. 分支不删，半年后 40 个分支不知道哪个是活的。
11. 提测前不备份数据库，改错数据只能重来。
12. 上线不留回滚方案，出问题现场想。

## 9. 每天收工前的 60 秒

```bash
git status                 # 有没有该提交的
git add -A && git commit -m "..."
git push
```

然后写 5 行日报。**这一天就算过完了。** 中断超过 3 天，这个项目基本就死了。
