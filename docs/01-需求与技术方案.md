# 01 需求与技术方案

> 这份文档扮演国内小公司里三份文档的角色：**简版 PRD + 数据库设计 + 接口契约**。
> 第 1 周照着它写代码；写的过程中发现它有问题，就改它，然后提交一个 `docs:` commit——这就是真实工作。

---

## 1. 业务背景（一句话）

公司 IT 支持靠微信群喊人，报修容易漏、处理没记录、月底没法统计。做一个内部工单系统：**谁报的、派的谁、卡在哪、多久修好，全都可查。**

目标（3 条，可验收）：

1. 员工在 1 分钟内能提交一张报修单，并随时看到进度。
2. 管理员能看到所有人的单，能派单、导出、看统计。
3. 每张单的每次状态变化都有记录，出问题能追溯到人和时间。

## 2. 角色与权限矩阵

| 能力 | 员工 EMPLOYEE | 技术员 ENGINEER | 管理员 ADMIN |
|---|:--:|:--:|:--:|
| 登录 / 查看自己信息 | ✅ | ✅ | ✅ |
| 创建工单 | ✅ | ✅ | ✅ |
| 查看工单范围 | 只看自己提的 | 只看派给自己的 | 全部 |
| 派单 / 改派 | ❌ | ❌ | ✅ |
| 接单 | ❌ | ✅（仅自己的） | ❌ |
| 完工 | ❌ | ✅（仅自己的） | ❌ |
| 评价 / 关闭 | ✅（仅自己的，已完成态） | ❌ | ❌ |
| 撤销 | ✅（仅自己的，未接单） | ❌ | ❌ |
| 导出 Excel | ❌ | ❌ | ✅ |
| 统计看板 | ❌ | ❌ | ✅ |

**两条铁律**（越权 bug 90% 出在这）：

1. 列表按角色过滤**只是体验**，`/tickets/{id}` 这类按 ID 的操作**必须再校验一次归属**。
2. 越权返回 `40300`；如果担心被拿来探测"这个 ID 存不存在"，返回 `40400` 也可以——但**全项目要统一**，别一半一半。

## 5. 工单状态机

### 5.1 状态与流转

```
                  ┌──────────── cancel ────────────┐
                  ▼                                │
   [CREATED] ──assign──▶ [ASSIGNED] ──accept──▶ [PROCESSING] ──finish──▶ [COMPLETED] ──rate──▶ [CLOSED]
      待派单               待接单                  处理中                  待评价                 已关闭
        │                     │
        └──cancel─────────────┴──▶ [CANCELLED] 已撤销
```

| 动作 | 允许的角色 | 起始状态 | 目标状态 | 副作用 |
|---|---|---|---|---|
| assign | ADMIN | CREATED / ASSIGNED（改派） | ASSIGNED | 写 `assignee_id`、`assign_time` |
| accept | ENGINEER（本人） | ASSIGNED | PROCESSING | 写 `accept_time` |
| finish | ENGINEER（本人） | PROCESSING | COMPLETED | 写 `finish_time`、`finish_remark` |
| rate | EMPLOYEE（本人） | COMPLETED | CLOSED | 写 `rating`、`rating_comment`、`close_time` |
| cancel | EMPLOYEE（本人） | CREATED | CANCELLED | 写 `close_time` |
| autoClose | 定时任务 | COMPLETED（超 7 天未评价） | CLOSED | 写 `close_time` |

**非法跳变一律 `40901`**，例如 `CREATED → COMPLETED`、`CLOSED → PROCESSING`。

### 5.2 并发怎么保证（这里是你面试的第一个亮点）

错误写法（新人 100% 会写）：

```java
Ticket t = mapper.selectById(id);      // 两个线程都读到 ASSIGNED
if (t.getStatus() != ASSIGNED) throw ...;
t.setStatus(PROCESSING);
mapper.updateById(t);                   // 两个都更新成功 → 一单被两人接
```

正确写法：**把"判断 + 修改"压进一条 SQL，用影响行数判断是否抢到。**

```sql
UPDATE ticket
   SET status = #{toStatus}, accept_time = NOW(), version = version + 1, update_time = NOW()
 WHERE id = #{id}
   AND status = #{fromStatus}       -- 关键：状态没变才更新
   AND deleted = 0;
```

```java
int rows = mapper.casUpdateStatus(id, from, to, ...);
if (rows == 0) throw new BizException(ErrorCode.STATUS_CONFLICT); // 40901
```

同一把锁在数据库层，单机多机都成立。`version` 字段可选（这里是锦上添花），面试讲清"用状态做条件更新"就够了。

## 6. 数据库设计

库名 `fixdesk`，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`（MySQL 8 默认）。

### 6.1 sys_user

```sql
CREATE TABLE sys_user (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  username    VARCHAR(32)  NOT NULL                COMMENT '登录名',
  password    VARCHAR(100) NOT NULL                COMMENT 'BCrypt 密文，绝不存明文',
  real_name   VARCHAR(32)  NOT NULL                COMMENT '姓名',
  dept        VARCHAR(32)  DEFAULT NULL            COMMENT '部门',
  phone       VARCHAR(20)  DEFAULT NULL            COMMENT '手机号（展示需脱敏）',
  role        VARCHAR(16)  NOT NULL                COMMENT 'EMPLOYEE/ENGINEER/ADMIN',
  status      TINYINT      NOT NULL DEFAULT 1      COMMENT '1启用 0禁用',
  deleted     TINYINT      NOT NULL DEFAULT 0      COMMENT '逻辑删除',
  create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_username (username)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户';
```

### 6.2 ticket

```sql
CREATE TABLE ticket (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  ticket_no      VARCHAR(24)  NOT NULL COMMENT '业务单号，如 R202610230001',
  title          VARCHAR(100) NOT NULL COMMENT '标题',
  description    VARCHAR(2000) NOT NULL COMMENT '问题描述',
  category       VARCHAR(16)  NOT NULL COMMENT 'NETWORK/HARDWARE/SOFTWARE/ACCOUNT/OTHER',
  priority       TINYINT      NOT NULL DEFAULT 2 COMMENT '1低 2中 3高',
  status         VARCHAR(16)  NOT NULL COMMENT 'CREATED/ASSIGNED/PROCESSING/COMPLETED/CLOSED/CANCELLED',
  creator_id     BIGINT UNSIGNED NOT NULL COMMENT '提单人',
  creator_name   VARCHAR(32)  NOT NULL COMMENT '冗余，列表免 join',
  creator_dept   VARCHAR(32)  DEFAULT NULL COMMENT '冗余，按部门统计用',
  assignee_id    BIGINT UNSIGNED DEFAULT NULL COMMENT '处理人',
  assignee_name  VARCHAR(32)  DEFAULT NULL COMMENT '冗余',
  assign_time    DATETIME     DEFAULT NULL,
  accept_time    DATETIME     DEFAULT NULL,
  finish_time    DATETIME     DEFAULT NULL,
  close_time     DATETIME     DEFAULT NULL,
  finish_remark  VARCHAR(500) DEFAULT NULL COMMENT '处理说明',
  rating         TINYINT      DEFAULT NULL COMMENT '1~5',
  rating_comment VARCHAR(200) DEFAULT NULL,
  version        INT          NOT NULL DEFAULT 0 COMMENT '乐观锁',
  deleted        TINYINT      NOT NULL DEFAULT 0,
  create_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_ticket_no (ticket_no),
  KEY idx_creator_time  (creator_id, create_time),
  KEY idx_assignee_stat (assignee_id, status),
  KEY idx_status_time   (status, create_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='工单';
```

三个索引不是凑数，每个都对应一条真实查询：

| 索引 | 服务的查询 | 最左前缀说明 |
|---|---|---|
| `uk_ticket_no` | 按单号精确查、单号唯一兜底 | — |
| `idx_creator_time` | 员工"我的工单"按时间倒序 | `creator_id` 必带，`create_time` 用于排序 |
| `idx_assignee_stat` | 技术员"我的待办"按状态筛 | `assignee_id` 必带 |
| `idx_status_time` | 管理员"按状态 + 时间"筛、统计 | `status` 必带 |

**反面教材**（你会犯的）：给 `title` 建索引然后用 `LIKE '%空调%'` —— 前导通配符直接让索引失效，白建。要么改成 `LIKE '空调%'`，要么上全文索引/ES（本项目不做，讲清楚就行）。

### 6.3 ticket_log

```sql
CREATE TABLE ticket_log (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  ticket_id     BIGINT UNSIGNED NOT NULL COMMENT '工单ID',
  action        VARCHAR(24)  NOT NULL COMMENT 'CREATE/ASSIGN/ACCEPT/FINISH/RATE/CANCEL/AUTO_CLOSE',
  from_status   VARCHAR(16)  DEFAULT NULL,
  to_status     VARCHAR(16)  DEFAULT NULL,
  operator_id   BIGINT UNSIGNED NOT NULL COMMENT '操作人（系统任务用 0）',
  operator_name VARCHAR(32)  NOT NULL COMMENT '冗余，日志页免 join',
  remark        VARCHAR(300) DEFAULT NULL COMMENT '如处理说明、评价内容',
  create_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_ticket (ticket_id, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='工单流转记录';
```

日志表只增不改不删，是审计和排障的依据。`operator_name` 冗余存一份，日志页就不用 join 用户表。

### 6.5 设计取舍（评审时被问到的点）

| 决策 | 选择 | 理由 / 代价 |
|---|---|---|
| 状态用 `VARCHAR` 还是 `TINYINT` | VARCHAR | 直接 `select` 就能看懂，排障和日志友好；状态少，索引体积无所谓。代价：改枚举要动数据 |
| 是否加 `status` 关联表 | 不加 | 6 个固定状态，加表是过度设计 |
| 冗余 `creator_name` / `assignee_name` | 加 | 列表页免 join，性能收益明确；代价是用户改名要同步（本项目用户资料基本不变，可接受） |
| 逻辑删除 | 保留 `deleted` | 工单不允许物理删除（审计要求）。注意：`uk_username` 与逻辑删除会打架，删用户时把 username 改成 `xxx_deleted_时间戳` |
| 单号生成 | `R + yyyyMMdd + 4 位序号` | 唯一索引兜底，冲突重试 3 次。真实做法是 Redis INCR 或号段表，本项目说明"为什么先用唯一索引重试"即可 |
| 金额字段 | 没有 | 涉及钱就要 `DECIMAL`，就要对账，本项目不碰 |

## 7. 接口契约

统一前缀 `/api`，全部 `Content-Type: application/json`，除登录外都要求 `Authorization: Bearer <token>`。

### 7.1 统一返回

```json
{ "code": 0, "message": "ok", "data": { }, "traceId": "8f3c1a2b9d4e" }
```

分页 `data`：

```json
{ "total": 137, "pageNum": 1, "pageSize": 10, "list": [ ] }
```

### 7.2 错误码

| code | 含义 | HTTP | 什么时候用 |
|---|---|---|---|
| 0 | 成功 | 200 | — |
| 40001 | 参数校验失败 | 400 | `@Valid` 没通过、枚举值非法、评分越界 |
| 40100 | 未登录 / token 无效或过期 | 401 | 拦截器拦下 |
| 40300 | 无权限 | 403 | 角色不对、不是自己的单 |
| 40400 | 资源不存在 | 404 | ID 查不到 |
| 40901 | 状态已变更，请刷新重试 | 409 | CAS 更新影响行数 0 |
| 40902 | 重复提交 | 409 | 同内容 5 秒内重复提单（可选） |
| 50000 | 系统异常 | 500 | 兜底，绝不把堆栈返给前端 |

### 7.3 接口清单

| # | 方法 | 路径 | 说明 | 角色 | 入参要点 |
|---|---|---|---|---|---|
| 1 | POST | `/api/auth/login` | 登录 | 匿名 | `username`, `password` |
| 2 | GET | `/api/auth/me` | 当前用户 | 全部 | — |
| 3 | POST | `/api/tickets` | 创建工单 | 全部 | `title`, `description`, `category`, `priority` |
| 4 | GET | `/api/tickets` | 工单列表（按角色自动限范围） | 全部 | `pageNum`, `pageSize`, `status`, `keyword`, `category`, `assigneeId` |
| 5 | GET | `/api/tickets/{id}` | 详情 | 全部 | — |
| 6 | GET | `/api/tickets/{id}/logs` | 流转记录 | 全部 | — |
| 7 | POST | `/api/tickets/{id}/assign` | 派单/改派 | ADMIN | `assigneeId` |
| 8 | POST | `/api/tickets/{id}/accept` | 接单 | ENGINEER | — |
| 9 | POST | `/api/tickets/{id}/finish` | 完工 | ENGINEER | `finishRemark`（必填，≤500） |
| 10 | POST | `/api/tickets/{id}/rate` | 评价关闭 | EMPLOYEE | `rating`(1~5), `comment`(≤200) |
| 11 | POST | `/api/tickets/{id}/cancel` | 撤销 | EMPLOYEE | `reason`（可选） |
| 12 | GET | `/api/tickets/export` | 导出 | ADMIN | 同列表筛选条件 |
| 13 | GET | `/api/stats/overview` | 统计看板 | ADMIN | `days`（默认 7） |

**接口写在前面的意义**：第 2 天把这张表定死，第 3 天之后你就不用再纠结"接口该叫什么"，每天只想着实现。这就是真实公司"契约先行"的做法。

## 8. 技术选型与理由

| 组件 | 版本 | 为什么选 | 坑（踩过才算会） |
|---|---|---|---|
| JDK | 17 | Spring Boot 3 最低要求，LTS | — |
| Spring Boot | 3.2.5 | 新项目标配，国内招聘主流 | `javax.*` 全变 `jakarta.*`，照老教程抄必报错 |
| MyBatis-Plus | 3.5.7 | 单表 CRUD 省一半代码，国内公司用得最多 | Boot 3 必须用 `mybatis-plus-spring-boot3-starter`；分页要手动注册 `PaginationInnerInterceptor` |
| MySQL | 8.0 | 本机已有，国内业务库主流 | 时区：JDBC URL 加 `serverTimezone=Asia/Shanghai` |
| Lombok | 最新 | 少写 getter/setter | IDEA 要装插件 + 开 Annotation Processing，否则满屏红 |
| springdoc-openapi | 2.3.0 | 自动生成 Swagger UI，替代手写文档 | 路径是 `/swagger-ui.html`；被拦截器拦了要加白名单 |
| jjwt | 0.12.5 | 轻量，无 Spring 依赖 | 0.12 的 API 和网上 0.9 教程完全不同，看官方 README |
| EasyExcel | 3.3.4 | 流式写，内存可控 | 别用 `POI` 的 `XSSFWorkbook` 全量写，1 万行就危险 |
| JUnit 5 + Mockito | 随 Boot | 测 service 层足够 | 别为了覆盖率去测 getter |
| 不选 Redis | — | JWT 无状态，无会话共享需求 | 讲清楚"什么时候才需要"就行 |
| 不选 Spring Security | — | 学习成本 vs 收益不划算；拦截器 60 行能实现 | **面试要主动说明**：生产项目安全要求高时该用 Security，我这里是权衡后的选择 |

**关于 Spring Security 的说明**（必须准备，否则被追问会露馅）：
本项目的鉴权 = 拦截器解析 JWT + `UserContext` 存当前用户 + service 里做角色/归属校验。
它缺的是：方法级注解鉴权、CSRF、密码策略、会话并发控制。这些 Spring Security 都能给，但配置成本对一个 4 周项目不划算。**升级路径**：加 `spring-boot-starter-security`，把拦截器换成一个 `OncePerRequestFilter`，用 `@PreAuthorize` 替代手写判断。

## 9. 非功能要求（初级岗最容易被忽略、也最容易加分）

| 项 | 要求 | 落地位置 |
|---|---|---|
| 参数校验 | 所有入参 DTO 加 `@Valid` + `@NotBlank/@Size/@Min`；枚举单独校验 | controller 层 |
| 密码 | BCrypt 存，登录失败统一提示"用户名或密码错误"（不区分哪个错） | service 层 |
| 敏感信息 | 返回值不包含 `password`；手机号中间 4 位打码；日志不打密码 | VO + 序列化 |
| SQL 注入 | 全部 `#{}`，禁止 `${}` 拼接；排序字段用白名单 | mapper |
| 越权 | 按 ID 操作必查归属；列表过滤只是体验 | service 层 |
| 日志 | 统一格式含 `traceId`；关键动作 `info`；异常 `error` 带堆栈；不 `e.printStackTrace()` | filter + logback |
| 性能 | 列表强制分页，`pageSize ≤ 100`；导出分批；统计走索引 | 全局 |
| 事务 | `@Transactional` 只包 DB 操作，不包远程调用/文件 IO | service 层 |
| 配置 | 密码走环境变量，`application-local.yml` 进 `.gitignore` | 配置 |

## 10. 五条设计决策（ADR 简版，面试可以直接讲）

1. **不用 Spring Security，用拦截器 + JWT**：4 周项目里配置成本高于收益；已知缺口（方法级鉴权）在文档里写明，不装作没有。
2. **不用 develop 分支**：一个人开发，`main + feature/*` 足够；多一个长期分支就多一份合并成本。团队超过 3 人再引入 develop。
3. **定时任务用 `@Scheduled` 单机跑**：没有分布式需求。多实例部署会重复执行，解法是分布式锁或 XXL-Job——知道就行，不实现。
4. **状态用字符串枚举而不是数字**：可读性换存储空间，状态少，划算。
5. **导出用 EasyExcel 分批 + 游标**：`limit offset` 深分页会越翻越慢，用 `where id > lastId` 走索引。
