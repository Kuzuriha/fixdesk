# 第 1 周：把链路打通（需求 → 设计 → 能跑能登录能提单）

## D1｜需求评审 + 建仓库（1.5h）

- **做**
  1. 通读 [01 文档](./01-需求与技术方案.md)，不许跳过"不做清单"。
  2. 让 AI 当**产品经理**和**测试**，分别挑一遍需求（prompt 在 [03 文档](./03-Git与协作流程.md) 第 4 节），把意见写进 `docs/review/D1-需求评审.md`。
  3. 把 15 个用例建成 Issue，打标签 `feat`/`bug`/`tech`，标优先级。
  4. 建 Gitee（或 GitHub）**私有**仓库，`main` 设为保护分支。
- **验收**
  - [ ] 评审记录里 ≥8 条意见，每条都有"结论：采纳/不采纳 + 理由"
  - [ ] Issue 看板 15 张卡，每张有验收标准
  - [ ] 仓库能 clone，第一版文档已推送
- **技术点**：用例（谁做什么）和需求（要什么）的区别；为什么"不做清单"比"要做清单"重要。
- **Git**：`day0-init.ps1` 已经替你提交了一次 `chore: bootstrap repo with project plan docs`；今天你自己再提交一条 `docs: 补充需求评审记录`（一次提交只做一件事，别拆成 5 个"update"）
- **卡住**：AI 给的意见太泛 → 追问"请指出需求里会导致返工的三处歧义，并给出你作为测试会怎么卡我"。

## D2｜表设计 + 接口契约（1.5h）

- **做**
  1. **先不看 01 文档**，自己手写 3 张表的字段和索引，再对照，把差异记下来（这是最值钱的 20 分钟）。
  2. 在 MySQL 建库建表，跑通 DDL，插入 3 个用户、5 条工单假数据。
  3. 把 13 个接口写成 `docs/design/接口契约.md`（方法/路径/入参/出参/错误码），写到"能照着写代码"的粒度。
- **验收**
  - [ ] `sql/schema.sql` 进仓库，能在空库一键执行
  - [ ] 每个字段有 `COMMENT`，每个索引能说清服务哪条查询
  - [ ] 接口文档里没有"待定"
- **技术点**：`utf8mb4` 与 `utf8` 的差别；唯一索引 vs 唯一约束；为什么索引列顺序重要（`assignee_id, status` 反过来就失效）。
- **Git**：`feature/02-db-design` → PR → 合并；commit 至少 2 个（表、接口文档）
- **卡住**：分不清该不该冗余字段 → 判断标准：这个字段会不会改？列表页是否每个请求都要它？两个都是"不会改/要"就冗余。

## D3｜骨架 + 统一返回 + 全局异常（1.5h）

- **做**
  1. start.spring.io 生成工程（Web / Validation / MySQL Driver / Lombok），手动加 MyBatis-Plus、springdoc 依赖。
  2. 配置 `application.yml` + `application-local.yml`（后者进 `.gitignore`）。
  3. 写 `Result<T>`、`ErrorCode` 枚举、`BizException`、`GlobalExceptionHandler`。
  4. 起服务，打开 `/swagger-ui.html`。
- **验收**
  - [ ] 启动无报错，控制台能看到 Tomcat 端口
  - [ ] 访问不存在的路径，返回统一 JSON 而不是 Whitelabel 错误页
  - [ ] 手动 `throw new BizException(...)`，返回对应 code，不返回堆栈
- **技术点**：`@RestControllerAdvice` 能兜住哪些异常；`@ExceptionHandler` 的匹配优先级；为什么不能把 `Exception` 的 message 直接返给前端。
- **Git**：`feat(common): 统一返回与全局异常处理`
- **卡住**：依赖下不下来 → 配阿里云镜像（03 文档 5.1）；Maven 版本报错 → 换 IDEA 自带 Maven 3.8。

## D4｜登录 + JWT + 拦截器（1.5h）

- **做**
  1. 造 3 个账号（员工/技术员/管理员），密码用 BCrypt 生成后写进 seed SQL。
  2. `POST /api/auth/login`：查用户 → 校验密码 → 签发 JWT。
  3. `JwtUtil` 生成/解析；`LoginInterceptor` 解析 token；`UserContext`（ThreadLocal）存当前用户。
  4. `WebMvcConfigurer` 注册拦截器，放行 `/api/auth/login`、`/swagger-ui/**`、`/v3/api-docs/**`。
- **验收**
  - [ ] 正确密码返回 token；错误密码返回 `40100`，且提示不区分"用户不存在/密码错"
  - [ ] 带 token 调 `/api/auth/me` 返回当前用户（不含密码）
  - [ ] 不带 token 返回 `40100`，不是 500
- **技术点**：拦截器和过滤器的区别（拦截器能拿到 HandlerMethod）；**ThreadLocal 必须在 `afterCompletion` 里 `remove()`**，否则线程池复用会串用户；JWT 无状态的代价——服务端无法主动让 token 失效。
- **Git**：`feat(auth): 登录与 JWT 鉴权`
- **卡住**：token 解析报 `JWT signature does not match` → 密钥长度不够（HS256 要求 ≥32 字节）。

## D5｜创建工单（1.5h）

- **做**
  1. `Ticket` 实体 + Mapper + Service + Controller。
  2. 单号生成：`R + yyyyMMdd + 4 位序号`，唯一索引冲突重试 3 次。
  3. 入参 DTO 加 `@Valid`（标题 ≤100、描述 ≤2000、分类必须是枚举）。
  4. 创建时同时写 `ticket_log`（action=CREATE），两张表一个事务。
- **验收**
  - [ ] 提单成功返回单号；同一天第二单序号 +1
  - [ ] 标题 101 字返回 `40001`，message 说清哪个字段错了
  - [ ] `ticket_log` 里有对应 CREATE 记录
- **技术点**：DTO / VO / Entity 为什么分三层（Entity 直接返回 = 泄露密码、字段改名就破坏接口）；为什么"先写主表再写日志"也在一个事务里。
- **Git**：`feat(ticket): 创建工单接口`
- **卡住**：`@Valid` 不生效 → 检查 controller 参数上有没有 `@Valid`/`@Validated`，异常有没有被全局处理器正确分类。

## D6｜列表 + 详情 + 流转记录（周末 2.5h）

- **做**
  1. 注册 MyBatis-Plus 分页插件，写列表接口：`status`/`keyword`/`category` 三个条件。
  2. 详情接口 + 日志列表接口。
  3. 列表用 VO 裁剪字段（不返回 description 全文）。
  4. 用 Apifox/Swagger 跑一遍 3 个角色的典型路径，截图存 `docs/demo/`。
- **验收**
  - [ ] `pageNum=1&pageSize=10` 返回 `total/list`，翻页数据不重复不丢
  - [ ] `keyword` 能同时搜标题和单号
  - [ ] 详情返回 3 条以内日志且按时间正序
- **技术点**：MP 分页插件是**改写 SQL 加 LIMIT**，不是查完再切；`count` 在深翻页时可能比主查询还慢；`LIKE '%x%'` 走不了索引的取舍。
- **Git**：PR 合并 + 打 tag `v0.1.0`
- **周五 30 分钟**：录 3 分钟屏，讲"现在能做什么、哪里还丑"。存 `docs/demo/w1.mp4` 或直接写文字版。

# 第 2 周：主流程闭环 + 权限（这周决定项目成不成立）

## D7｜状态机 + 派单/接单（1.5h）

- **做**
  1. `TicketStatus` 枚举 + `canTransferTo(target)`，把 5.1 的转移表写死。
  2. 抽一个 `transition(id, from, to, action, operatorId)` 方法，内部用 **CAS SQL**（`where status = ?`），影响行数 0 抛 `40901`。
  3. `assign`（管理员，可改派）、`accept`（技术员，只能接自己的）。
  4. 每次流转写 `ticket_log`。
- **验收**
  - [ ] `CREATED → COMPLETED` 被拒，返回 `40901`
  - [ ] 同一单重复 `accept`，第二次返回 `40901`
  - [ ] 每次成功流转，日志表多一条，`from_status/to_status` 正确
- **技术点**：为什么"先查再改"有并发窗口；**用状态做更新条件 + 判断影响行数**是这里唯一正确的写法；事务回滚后 CAS 也要回滚（同一事务内）。
- **Git**：`feat(ticket): 状态机与派单接单`
- **卡住**：`rows == 0` 分不清是"状态不对"还是"单不存在" → 先查一次做区分（多一次查询换准确报错，值）。

## D8｜完工 / 评价 / 撤销（1.5h）

- **做**
  1. `finish`（技术员，必须 PROCESSING，`finishRemark` 必填）。
  2. `rate`（员工，必须 COMPLETED，评分 1~5）→ CLOSED。
  3. `cancel`（员工，只能 CREATED 撤销）。
- **验收**
  - [ ] 技术员 A 完工技术员 B 的单 → `40300`
  - [ ] 评分传 6 → `40001`
  - [ ] 已接单的单调 `cancel` → `40901`
- **技术点**：校验顺序固定为 **身份 → 归属 → 状态 → 参数**（顺序错了会出现"越权的人先看到参数错误"这种信息泄露）；事务里异常必须抛出去才会回滚。
- **Git**：`feat(ticket): 完工、评价与撤销`
- **卡住**：`@Transactional` 不回滚 → 检查是不是自己 try-catch 把异常吞了。

## D9｜数据权限（1.5h）

- **做**
  1. 列表按角色加范围：员工=自己提的；技术员=派给自己的；管理员=全部。
  2. 详情/流转/操作接口统一走一个 `assertCanAccess(ticket, user)`。
  3. 管理员派单时校验被派人角色必须是 ENGINEER。
- **验收**
  - [ ] 员工 A 用自己的 token 查员工 B 的单 ID，返回 `40300`
  - [ ] 员工列表里只有自己的单，`total` 也对
  - [ ] 管理员派给一个 EMPLOYEE，返回 `40001`
- **技术点**：**必须在 SQL 层加条件**，不能查全量再内存过滤——否则分页的 `total` 和条数全错；`40300` 与 `40400` 的选择（防 ID 探测）。
- **Git**：`feat(auth): 工单数据权限`
- **卡住**：每个接口都在重复写权限判断 → 抽 `TicketAccessService`，别用 AOP 硬套（现在还没到那个复杂度）。

## D10｜操作日志 + 审计（1.5h）

- **做**
  1. 所有流转/操作统一写日志（含系统任务，`operator_id=0`）。
  2. 日志查询接口支持管理员查任意工单。
  3. 日志表不参与业务查询，只做展示和追溯。
- **验收**
  - [ ] 一张单从创建到关闭，日志能完整还原 5 步
  - [ ] 日志里有操作人姓名、时间、前后状态
- **技术点**：什么时候用 AOP（横切、格式统一），什么时候直接写（一步操作只写一条，AOP 反而绕）；日志表为何只增不改。
- **Git**：`feat(ticket): 流转日志与审计`
- **卡住**：AOP 里拿不到方法内的业务数据 → 说明这里不该用 AOP，改在 service 里显式写。

## D11｜单元测试（1.5h）

- **做**：JUnit5 + Mockito，测状态机：6 个合法转移 + 2 个非法转移 + 1 个越权 + 1 个单号生成。
- **验收**
  - [ ] `mvn test` 全绿
  - [ ] 覆盖所有枚举转移组合（可以参数化测试）
- **技术点**：为什么测 service 不测 controller（controller 是胶水）；Mockito mock 掉 mapper 后"事务"其实没被测到——知道这个局限。
- **Git**：`test(ticket): 状态流转单元测试`
- **卡住**：测试跑不起来 → 检查 `spring-boot-starter-test` 是否引入、JDK 版本是否对齐。

## D12｜提测 + 修 bug（周末 3h）

- **做**
  1. 按 [03 文档](./03-Git与协作流程.md) 第 6 节的 20 条用例，手工全跑一遍。
  2. 每个问题建 bug Issue（复现步骤/期望/实际/环境）。
  3. 修完回归，填提测单。
- **验收**
  - [ ] 20 条用例全过，或已知问题有明确记录和"暂不修"结论
  - [ ] 提测单填完，版本号 `v0.5.0`
- **技术点**：冒烟测试 vs 回归测试的边界；bug 单写不清等于没提。
- **Git**：bug 修复走 `fix/xxx` 分支，每个 bug 一个 commit；打 tag `v0.5.0`
- **周五 30 分钟**：复盘这周"哪一天最卡"，写 3 行。

# 第 3 周：真实业务里的脏活（这周让你从"会写接口"变成"能上线"）

## D13｜Excel 导出（1.5h）

- **做**
  1. `GET /api/tickets/export`，EasyExcel 写 xlsx。
  2. 分批：每批 1000 条，用 `where id > lastId` 游标翻页，不用 `limit offset`。
  3. 文件名带时间戳；导出加管理员权限校验。
- **验收**
  - [ ] 1 万条数据 5 秒内导出，JVM 内存不飙
  - [ ] 文件能用 Excel 打开，中文不乱码
- **技术点**：`XSSFWorkbook` 全量在内存 vs EasyExcel 流式；`limit 100000, 1000` 为什么会越翻越慢（要扫前 10 万行）。
- **Git**：`feat(ticket): Excel 导出`
- **卡住**：中文乱码 → 响应头加 `Content-Disposition` + `URLEncoder`。

## D14｜统计看板 + explain（1.5h）

- **做**
  1. `/api/stats/overview`：各状态数量、今日新增、今日完成、平均处理时长（accept→finish，单位小时）。
  2. 用 `group by status` 一条 SQL 拿状态分布，避免 5 次 `count`。
  3. 对每条统计 SQL 跑 `explain`，把结果贴进 `docs/design/性能记录.md`。
- **验收**
  - [ ] 5 个指标正确，平均时长手算能对上
  - [ ] `explain` 的 `type` 不是 `ALL`，`rows` 在合理范围
- **技术点**：`count(*)` 在 InnoDB 要扫索引，数据大了会慢；什么时候该加汇总表（现在不需要，说清触发条件）。
- **Git**：`feat(stats): 统计看板`
- **卡住**：`avg` 算出负数或极大值 → 有的单 `accept_time` 为空，`AVG` 前要 `where accept_time is not null`。

## D15｜定时任务 + 时区（1.5h）

- **做**
  1. 每小时扫描 `status=CREATED` 且创建超 2 小时的单，写一条提醒日志。
  2. 每天凌晨 2 点把 `COMPLETED` 超 7 天未评价的单自动 CLOSED。
  3. `@Scheduled(cron = "0 0 * * * ?")`，任务开关放配置。
  4. 任务方法加注释说明"单机执行，多实例需分布式锁"。
- **验收**
  - [ ] 手动把某条 `create_time` 改到 3 小时前，下次执行能扫到
  - [ ] 自动关闭写 `AUTO_CLOSE` 日志，`operator_id=0`
  - [ ] 重启服务不会重复执行（单机）
- **技术点**：Spring cron 是 **6 位**（秒 分 时 日 月 周），和 Linux 5 位不一样；服务器/容器时区是 UTC 时，cron 会在错误的时间跑——`TimeZone` 显式指定；多实例一定重复执行。
- **Git**：`feat(job): 超时提醒与自动关闭`
- **卡住**：任务不触发 → 主类上有没有 `@EnableScheduling`。

## D16｜日志 / traceId / 脱敏（1.5h）

- **做**
  1. `logback-spring.xml`：按天滚动，保留 7 天，单文件 100MB 上限。
  2. Filter 生成 `traceId` 放 MDC，返回体里也带；日志格式 `%X{traceId}`。
  3. 关键动作打 `info`（谁对哪张单做了什么）；异常打 `error` 带堆栈。
  4. 手机号打码工具（`138****1234`），日志和返回值都用它。
- **验收**
  - [ ] 用一次请求的 traceId `grep` 日志，能看到完整的 6 行链路
  - [ ] 日志文件里搜不到明文手机号和密码
- **技术点**：日志级别怎么选（`debug` 只在本地开）；日志也占 IO，别在循环里打；`printStackTrace` 会让日志丢失上下文。
- **Git**：`chore(log): 日志规范与 traceId`
- **卡住**：MDC 在异步线程里丢了 → 要手动传递（这就是为什么线程池里 traceId 会断）。

## D17｜故障演练①：并发抢单（1.5h）

- **做**
  1. 用 JMeter 或 Postman 并发 20 次，对同一张 `ASSIGNED` 单调 `accept`。
  2. 记录结果：成功几次？如果 >1，就是 bug。
  3. 定位：把 CAS 改成"先查再改"复现一次，再改回来——**亲手制造一次，才知道为什么要这么写**。
  4. 修复后重跑，写进 `docs/postmortem/并发抢单.md`。
- **验收**
  - [ ] 20 并发只有 1 次 200，其余 19 次 `40901`
  - [ ] 复盘文档有"现象-假设-验证-结论"四段
- **技术点**：怎么造并发（JMeter 线程组/Postman Runner）；为什么本地压测结果不能代表线上。
- **Git**：`fix(ticket): 并发接单重复成功`
- **卡住**：并发起不来 → 单机 CPU 少的话，20 线程足够，别追求大数字。

## D18｜故障演练②：导出 OOM / 慢查询（周末 2.5h）

- **做**
  1. 造 10 万条工单（写个循环插入的 SQL 或小脚本）。
  2. 先用全量 `POI` 写法导出一次，观察内存和耗时（大概率卡死或 OOM）。
  3. 换成 D13 的分批 + 游标写法，再测。
  4. 记录前后对比：耗时、峰值内存、`explain` 结果。
- **验收**
  - [ ] 有"优化前 / 优化后"的表格数据
  - [ ] 知道 OOM 时该看什么（`jmap -histo`、GC 日志）
- **技术点**：`-Xmx` 设小了会 OOM，设大了 GC 时间长；"能跑通"和"能上线"是两件事。
- **Git**：PR + tag `v0.9.0`
- **周五 30 分钟**：更新 README 的"已知问题"一节。

## 学习资料的取舍

- **优先官方文档**：Spring Boot Reference、MyBatis-Plus 文档、jjwt README。比视频课准确，且版本对得上。
- **报错**：先把完整报错原文丢给搜索引擎/AI，让它解释"这个异常在说什么"，再自己判断。
- **不要**：为了"打基础"去刷 40 小时视频课、去读 Spring 源码。你现在缺的是手感，不是原理深度。原理等做完再补，效率高 10 倍。
